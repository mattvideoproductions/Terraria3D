# Lessons from the Terraria 3D mod (for every 3DS plugin port)

These are the mistakes made and the discoveries along the way, v0.2.0 to v0.5.0. Read this before writing hardware-facing code.

## Hardware crashes and black screens (the emulator passed every one of these)
1. **Instruction cache.** v0.2.0 crashed the kernel at boot. `svcInvalidateInstructionCacheRange` runs in whatever process is current (it was i2c), which caused a data abort. Always use `svcInvalidateEntireInstructionCache`, as CTRPF does.
2. **Lazy VRAM allocation.** Allocating right-eye buffers in-world failed on hardware because game textures fill VRAM. Emulator tests had the 3D factor at 100 from boot, which hid this. Reserve stereo memory early (at the title screen), and always test with the slider at 0 at boot, raising it in-world.
3. **FCRAM display buffers.** Buffers from the game's own allocator showed BLACK on hardware (likely non-linear or cached memory). Use VRAM or proper linear memory.
4. **Plugin memory.** The plugin's ~5 MiB came out of game memory, so the game's own texture allocation failed. The result was an svcBreak when the world map opened. `UsePrivateMemory: true` in `.plgInfo` fixed it; keep it on. A similar dump recurred once afterwards, so it's not proven fully fixed.
5. **Process exit.** Deleting the CTRPF menu after `menu->Run()` returns crashed in `~MenuFolderImpl`. Don't free anything at shutdown.
6. **Input.** Circle Pad Pro / C-stick input through the game's own ExtraPad (ir:USER) read "connected" but always gave 0,0 on hardware, while it worked in Azahar. Fix: open ir:rst in the plugin (`irrstInit`/`irrstScanInput`/`irrstCstickRead`, raw ±~140). Never gate on the game's "connected" flag.
7. **Display LUT.** The colour LUT registers (PA 0x10400480/484 top, 0x10400580/584 bottom, accessed as PA|0x80000000) aren't emulated by Azahar. Anything display-controller-level must be tested on hardware.
8. **Suspected (being investigated in v0.5).** White tiles and outlines in dark areas when per-layer stereo replays draw runs for the right eye. Likely stale or recycled vertex/colour data or missing state at replay time. Expect GPU-reads-after-CPU-overwrites problems that the emulator never shows: flush the data cache, and don't reuse memory the GPU will still read later in the frame.

## Emulator limits (Azahar)
- It hides cache, VRAM-capacity, ir:USER, timing and display-LUT differences. Passing the emulator is not proof.
- The 3D slider can't be changed at runtime: the hotkey and writes to 0x1FF81080 are ignored. Relaunch with `-Factor`.
- Emulator frame timing isn't hardware timing. Use hardware perf logs: the plugin writes `SD:/luma/plugins/<tid>/t3d_log.txt` once per second. Read it first whenever the card comes back.
- Only one agent drives the emulator or desktop at a time.

## Method that worked
- Identify draw passes by giving each pass a unique horizontal shift, then measuring the shifts in a screenshot (`tools/measure_shifts.py`). Name passes from evidence, not guesses (an early guess mislabelled ground vs trees).
- Verify struct fields from the disassembly before using them. A guessed "consumable" offset (0x6A) was wrong; the real one is +0x75 bit 0x20.
- Version-check the exact title and update (full .text CRC) and refuse to patch anything else.
- Check original instruction words before hooking (`Install(addr, fn, expectedWord)`).
- Log context alongside FPS (3D on or off, slider, preset, zoom). In the v0.4.3 stress test, top-screen render CPU stayed ~8.5 ms while fps fell to the 30s, which proved the bottleneck was elsewhere (game logic or GPU), not the stereo.
- Make visual mods reversible at runtime: the UI theme rewrites texels only if they still hold the expected value, so Stock restores them exactly.

## Tooling mistakes
- A script named `dis.py` shadowed Python's stdlib `dis`, breaking capstone. Don't name scratch files after stdlib modules, and run Python with `-I`.
- Heredoc/Python edits turned `"\\n"` into real newlines in C++ strings. Check string literals after scripted edits.
- In the Azahar key map, "cright" is the circle pad, not the C-stick. The C-stick needed explicit scan codes.
- Windows SD: after a Shell eject the reader shows size 0 until the card is reseated.

## Workflow rules from the user
- Patch-only: never distribute game files. Never use the leaked 4J source. Never touch console system files.
- The user tests on hardware (New 3DS XL, plus a Japanese Old 3DS running US games via Luma region-free and locale emulation). Make defaults sane, and keep every option reversible.
- Sharing is GitHub and YouTube only.

## Added from the Minecraft 3D mod (2026-10-28)
- **VRAM-A is a budget, not free space.** Minecraft 1.9.19 leaves about 9 KiB of VRAM-A spare. While loading, it allocates a 2.625 MiB texture area (0x4F0284) and never checks the result. Our 911 KiB right-eye buffers in VRAM-A made that allocation return 0. The game then DMA'd to address 0 and hung on "Loading" at every slider value. The emulator reproduced this. Map the game's VRAM use before taking any; put right-eye buffers in VRAM-B, below 0x1F5F8000, because nngx uses the last 32 KiB itself. Check free space first, and leave stereo off rather than allocate into the game's space.
- **Dead features get deleted, not just disabled, across updates.** Minecraft v1.0 has a complete stereo renderer behind a kill-switch byte. The 1.9.19 update removed it entirely. Always RE the exact version that runs on the console.
- **Matt records videos on this PC.** Emulator automation that activates windows or sends keybd_event input ruins his takes. Set Azahar's [Audio] volume to 0 before every launch. Prefer focus-free input (minecraft-3ds `tools/azahar_bgkeys.ps1`, which PostMessages the window and starts it minimized without activating it). Stop all desktop driving the moment he says he's recording.
- **A CTRPF hook on the GSP event thread runs on a ~4 KiB stack.** Format OSD strings on the plugin thread; only draw them there.
- **CTRPF breaks the game's own C-stick on New 3DS (Minecraft v0.1.0 on hardware).** By default, CTRPF calls libctru `hidInit()` before the game starts, and on New 3DS that runs `irrstInit()` (IRRST Initialize). Games that read the C-stick through ir:USER (SDK ExtraPad / Circle Pad Pro path: Minecraft, very likely Terraria too, see #6) then get 0,0. Azahar doesn't show it. Fix: in the plugin, `extern "C" bool hidShouldUseIrrst(void){ return false; }` (overrides libctru's weak symbol). Never call irrstInit in a plugin unless the game itself uses ir:rst.

## Test conditions
- **Cheats change performance.** Terraria's Fullbright cheat lights every tile, so the game draws every cave backdrop cell it normally skips in darkness. With it on, caves locked to 29.9 fps; with it off they ran 55-60 (v0.5.1 test, 2026-10-28). Torch-heavy areas are the real worst case (29-39). Always log which cheats are on, and benchmark with gameplay cheats off.
- **The display DMA size follows the LEFT framebuffer only (Minecraft v0.2.0).** The SDK's `nngxSwapBuffersByAddress` sets the LCD format register's DMA-size bits (8-9) from the left address alone: FCRAM gives 0x100 (8-word bursts), VRAM gives 0x300. FCRAM can't do size 3 and goes black, which probably explains #3: Terraria had a VRAM left eye and an FCRAM right eye. A VRAM right eye behind an FCRAM left eye ran with small bursts from the busy VRAM bank. Minecraft v0.1.1 showed "glitchy lines" on hardware that moved with bottom-screen activity, and Azahar showed nothing. **Keep both eyes in the same memory type.** Best is VRAM for both, as Terraria's working setup has it. (Fix still pending hardware confirmation.)
- **Don't assume the game's triple buffer is round-robin.** Minecraft 1.9.19 picks the first free display index (0, else 1, else 2), so it usually alternates 0/1. Any scheme that keeps an older image on screen, such as alternate-eye stereo, needs its own buffer rotation.
- **Measure the GPU before you design around "GPU slack".** Inferring CPU-bound from short present() waits was wrong in-world. Timing RunCmdlist → cmdlist-done showed the GPU at 20 ms of a 24 ms frame. Log GPU time from the very first build.
- **Alternate-eye stereo needs turn compensation.** If the eyes are rendered one frame apart, a camera turn adds false disparity of about yaw-rate × frame time. In Azahar that flipped the horizon in front of the screen. Shifting the older eye by the projected camera change fixes the world. The side effect is that HUD/hand drawn into that image wobble during turns.
- **A projection-shear stereo has no built-in limit on how far things come out of the screen.** Disparity is s·px·(1 − C/D), which runs to minus infinity as D gets small: −56 px against a wall with C = 1.5, −148 px with C = 4. Choose the zero-parallax distance from the nearest the camera can ever get to a surface: C = Dmin·(1 + cap/px). Also edit only the top screen's matrices, because the bottom screen goes through the same uniform path (in Minecraft, an aspect test |m5/m0| ≈ 400/240 does this).
- **Automatic quality fallbacks must not change the picture's look, and must be tuned at hardware frame rates (Minecraft v0.3.0 → v0.3.1).** A "governor" that dropped Comfort 3D to the flat parallax plane for 10 s after 6 late frames out of 60 looked sensible in Azahar (60 fps). On hardware at 20-30 fps nearly every frame is late, so it tripped on every retry. Matt saw a 10 s flat / 1 s 3D cycle and disliked the switching more than the low fps. A stable, slightly worse mode beats a flipping one. Per-frame failures: repeat the last good stereo pair (one repeated frame) rather than show one 2D frame. Also, a fallback that reports "3D off" to other systems (render distance, leaves) can trigger rebuilds that make the next retry fail harder.
- **Always write a cheap diagnostic log, not only when a debug option is on.** Minecraft v0.3.0 logged only with "Log stats to SD", so the first hardware session left no data. Write a few counters every ~10 s from the plugin thread (no per-frame I/O), with a size cap.
- **A refused or overridden setting must show what is really in effect, in the menu itself (Minecraft v0.3.2).** v0.3.0's render distance 6 was refused by a memory guard that could never pass in a world (one 11 MiB game heap is always full once a world loads). The only signal was a 2-second notice, and the menu kept the name set at selection time. Matt concluded "stuck at 4" and "auto doesn't work". Menu entries for anything the plugin can refuse, clamp or apply later must be refreshed from the live values (e.g. `6 refused (low memory), 4 used`, `4 -> 3 in 3D (auto)`), and every change or refusal must be logged.
- **A memory guard needs evidence about which heap matters.** A rule like "every big heap must have X free" can fail forever on a pre-sized pool that the game fills on purpose. Log the heaps by slot at each setting first, then guard the heap that actually grows.
- **Size caps on logs must rotate, not stop (Minecraft v0.3.2).** A cap that silently stops logging once the file is big stops it for every later session too. Rename to `*_old.txt` at boot (and when over the cap), and write a boot line with the version and settings, so every log explains itself.
- **Log state changes as events, not only as periodic counts.** For "it flips between X and Y", write one line per transition with the time, from→to, reason, frame time and context. Queue it from the game thread in a lock-free ring, write from the plugin thread at most once per second, and rate-limit flapping. Counts every 10 s can't tell one long fallback from a hundred short ones.
- **Check the game's real HUD scale before promising a "smaller pixel-perfect HUD".** Minecraft 1.9.19's top HUD is already 1 screen pixel per GUI pixel (10-px font `mc_10`, 9-px crosshair; the GUI-scale index is already at the table minimum). Anything smaller is fractional. A projection-level scale of the GUI ortho (top screen, aspect-checked) is cheap and reversible, but it shrinks toward one point, so edge-anchored parts move inward and full-screen GUI quads shrink too.
- **Drop held/repeated frames after a long gap.** A "repeat the last good frame" fallback must forget that frame after HOME, sleep or any gap of more than ~200 ms, or it can re-show a picture from before the suspend.

## Added in Terraria v0.5.4 (2026-10-29)
- **Read what the game's own mode switches turn off.** Tap-to-move picked items but never placed them on hardware because the game's A-button carry disables touch on every slot (a recursive Widget "disable" on the list). Two releases of hook tuning missed it; one RPC read of the live objects in Azahar found it. When a UI feature "does nothing", dump the widget/state objects in the emulator before theorising about timing.
- **Get touch into the emulator without the window.** Synthetic mouse messages to Azahar's Qt 6 window did nothing, and Azahar's RPC cannot write plugin memory or the linear heap. A tiny hook on the game's touch read that copies a mailbox in the dead padding after `.text` (writable over RPC, never written on hardware) gives focus-free, scriptable touch. Use the same trick for other input in future ports.
- **An emulator crash dialog steals focus.** A guest exception pops "An exception occurred" as a new foreground window. Never call game functions from test hooks you haven't checked (calling the cheat dispatcher from the input hook crashed). Kill Azahar at once if a dialog appears, and keep test injections to plain data.
- **Check "the mod did it" against a stock run.** The green wall-seam lines Matt saw are in the stock game too (same saved world, plugin off). Save the world in-game, relaunch with `-NoPlugin`, compare pixels.
- **Closing the CTRPF menu can trip the game's own pause.** Terraria's main loop pauses after the plugin menu closes. Watch for page changes right after the menu closes and undo them only when the menu was opened from play.


## Added in Terraria v0.6.0, the Old 3DS build (2026-10-29)
- **Pace the swap, not the kick.** A 30 fps lock placed after nngxSwapBuffers only spaced out command-list kicks. After any late frame the screen would still go 3 VBlanks then 1, and a histogram measured at the same place would read "all 2-VBlank". The audit caught it before hardware did. Wait before the call that decides what is shown (here, before WaitCmdlistDone + SwapBuffers), and measure the display gap right after it.
- **Check the game's timestep before capping the frame rate.** Terraria adds the real dt and ticks per 1/60 s, so at 30 fps it runs 2 ticks per frame and the game speed holds. A no-catch-up patch would then halve the game speed, so the two must be mutually exclusive by menu choice, not by flipping .text at runtime.
- **Old 3DS plugin memory comes from a different region.** Luma takes the plugin block from the APPLICATION region on New 3DS (the cause of #4) but from the SYSTEM region on Old 3DS (outside mode 3). Log both regions at boot and in play. **Wrong conclusion, corrected in v0.6.1:** the game does *not* keep its memory. See below.
- **A compile-time flag can prove "no regression".** The build is reproducible, so a clean rebuild of the New 3DS target with every Old 3DS change behind `#ifdef T3D_O3DS` must give the same md5 as the shipped release. Check that after every edit.
- **Batch SD writes on slow consoles, but not events.** Write per-second lines in ~5 s batches. Write events, settings and failures at once, and anything from the first seconds after boot, so a crash or freeze still leaves the lines that explain it.
- **One .3gx per title folder.** Luma loads a single plugin from `/luma/plugins/<tid>/`. The New and Old 3DS builds share the file name and the log path, so the install notes must say "replace", never "add".

## Added in Terraria v0.6.1, the Old 3DS crash fix (2026-10-29)
- **On Old 3DS, every MiB of plugin memory is a MiB less for the game, even though it comes from the SYSTEM region.** Luma allocates the block in the game's process, so it counts against the game's commit limit. The SDK's `nninitStartUp` sizes the heaps from `APPMEMALLOC - committed`. v0.6.0's 5 MiB block cost the game 5 MiB of main heap, and title loading died with `bad_alloc` → svcBreak at 13 s. The clue was in the hardware log: "app free 5.00M" all session, memory the game never took. Use `MemorySize: 2MiB` on Old 3DS, and read the game's heap setup before choosing a size.
- **CTRPF takes a 1 MiB "search" heap before PatchProcess.** `InitHeap()` does `operator new(0x100000)` for the cheat search engine. In a 2 MiB block that aborts the plugin before your code runs. Fix: a global `operator new` that serves that one request from a small static block, then set `Heap::__ctrpf_heap_size` in PatchProcess (the pool initialises lazily). Also set `AllowSearchEngine = false` and `TryLoadSDSounds = false`.
- **A full VRAM is a budget, again (Terraria this time).** After the title loads, stock Terraria leaves 11.9 KiB of VRAM free. Our right-eye VRAM doesn't fail: it quietly pushes 1 MiB atlas pages into the game's device heap, which on Old 3DS has 1.3 MiB spare. Read the game's VRAM allocator (`0x8B8000`, `tools/azahar_vram.py`) and heaps (`tools/azahar_game_heaps.py`) over RPC, then pay for what you displace (here, device heap +1 MiB from main via one immediate in `nninitStartUp`). Keep the footprint under one page if you can: 607.5 KiB pushed out one page, 1.09 MiB pushed out two.
- **When the emulator doesn't model a cost, simulate it.** Azahar doesn't charge the plugin block to the game, so a plain run was 5 MiB too generous. A test-only patch that subtracts the charge in `nninitStartUp` reproduced the hardware crash (svcBreak at 11 s, with stereo off). After that every fix could be tested at hardware memory. Give such builds their own version string ("-TEST-EMULATOR-ONLY") so they can never ship by mistake.
- **Bisect the crash before theorising.** The suspects were vblank pacing, threads, the right-eye copy and the display-measure slot. Build flags that removed stereo, the allocations and the render target one at a time pointed at memory within an hour. A mode-switch theory would have stayed unproven.
- **Log the game's own heaps, not only the OS regions.** OS "free" figures can't show a fixed-size game heap running out. The Old 3DS build now walks the game's ExpHeap free lists every 10 s (read-only, range-checked). It also writes a `PANIC` line with those numbers from hooks on the game's svcBreak and failed-result paths, so the next hardware crash explains itself.
- **Azahar's software keyboard dialog takes focus.** Naming a character or world opens a modal Qt dialog titled "Azahar", which becomes the foreground window even when the main window is minimised. Answer it at once with PostMessage `WM_CHAR` + Enter (`tools/azahar_swkbd.py <name>`), then minimise Azahar again. Don't do this while Matt is recording.

## Added in Terraria v0.7.0, Old 3DS per-layer depth (2026-10-30)
- **A displaced page has slack: use it before you redesign.** The flat right-eye buffers (607.5 KiB) pushed out one whole 1 MiB atlas page, leaving 416 KiB of VRAM-B idle. A cropped 240x400 render target (375 KiB, instead of the game's power-of-two 256x512) fit into that hole at zero extra game memory. Before you build a complicated zero-VRAM scheme, map what your own allocations already cost (`tools/azahar_vram.py`).
- **Render targets don't have to be power-of-two.** nn::gd only checks power-of-two for mipmapped textures (levels > 1). The game's own 240x320 bottom target proves it on hardware. Read the validation code rather than assuming PICA texture rules.
- **The game's allocator may quietly fall back to the other bank.** Terraria's VRAM callback retries a failed VRAM-B request in VRAM-A when a global byte is set (0x10DB28 / `*0x633D94`). That would displace a different page. Clear such fallbacks around your own allocation, and check the address you actually got (`res+0x1C`).
- **Prove the layout in the log, not only in the emulator.** The plugin logs its VRAM room check once and `vram pages A 1 B 2` every 10 s. If the console fills VRAM in a different order, the first hardware log says so before anything crashes.
- **Read display buffers from screenshots, not guest VRAM.** Azahar keeps rendered results in host textures, so emulated VRAM reads back as garbage. Measure eye shifts from an RPC screenshot in side-by-side (half-width) mode at scale 2, where each eye is 400 px wide, 1:1. In "full width" side-by-side mode the RPC shot shows only part of each eye. Calibrate with flat mode first (12 px measured as 12).
- **RPC heap walks race the game.** One `azahar_game_heaps.py` read showed 0.04 MiB free (a torn walk). Repeat reads before you believe a scary number.
- **An until-loop waiting for a log line can miss a line that was already written.** Count the matches before launching the emulator, not after.

## Added in Terraria v0.5.6, the New 3DS surface crash (2026-10-31)
- **The New 3DS has a memory budget too, just a bigger one.** v0.5.5 crashed on hardware after ~18 min of surface play: the game's texture create (`0x1134E8`, called at `0x26ABF0` with placement 1 = FCRAM only, a 128x128 format-2 texture read off the dump's stack) failed and the caller sent the result to the fatal handler `0x145CB0` → svcBreak `0x13722C`. Terraria sizes its device heap (linear FCRAM, 73 MiB on New 3DS) so that only 3.24 MiB is free at the title; our right-eye VRAM pushes atlas pages into it, leaving 1.74 MiB. The same fix as the Old 3DS build applies: move memory from the main heap (~18 MiB free on New 3DS) with the `movne r4,#0x4900000` immediate at `0x108AB4` (+4 MiB in v0.5.6; with main another 5 MiB lower in a test build, creating an expanded world still left 7.36 MiB free, largest block 5.09). Measure both heaps with `tools/azahar_game_heaps.py` before and after any feature that takes VRAM.
- **Decode the fatal caller's stack frame, not just the call chain.** The 820-byte Luma dump still held the failing call's descriptor (`w 0x80, h 0x80, format 2, placement 1`) at the caller's `sp+8`. That told a small FCRAM texture from a big atlas page or bad parameters in minutes.
- **What grows the device heap on hardware was not reproduced in Azahar.** Surface walking, a full-width teleport, nightfall, rain, enemies, 40 new item types and the world map (a fixed 0.89 MiB, kept until the game closes) left it flat. The New 3DS build now logs `mem game main ... dev ... (min ...)` every 10 s plus a PANIC line from hooks on svcBreak `0x13722C` and the failed-result handler `0x13B16C`. `0x145CB0` itself is not hooked (its first instruction is PC-relative); it tail-calls svcBreak with r0 = r1 = 0, so the PANIC line also lists the first four game .text words found on the stack (the callers). The first hardware log should show the device heap "of 77.00M"; 73.00M means the patch did not apply.
